> **Статус:** завершён — все 10 зон прогоняются, кластеризация чанками + ретрай (DeepSeek)
> **Дата:** 2026-10-20
> **Связанные документы:** [plan.md](./plan.md), [plan-m0.md](./plan-m0.md), [requirements.md](../docs/requirements.md), [decisions.md](../docs/decisions.md), [AGENT.md](../AGENT.md)

## Цель и Definition of Done

Перевести конвейер из «вхолостую» (M0) в рабочий недельный прогон по всем 10 зонам:
реальные эмбеддинги (bge-m3), реальный LLM (Ollama для dev / DeepSeek для прод),
семантический отбор по зоне, кластеризация сигналов и черновой дайджест без верификации.

**Приёмка:**

- `uv sync` + `pytest` зелёный.
- Прогон по **всем 10 зонам**: RSS + fetch_url (+ опц. поиск RU) → фильтр по зоне
  (bge-m3) → кластеризация (LLM) → строки `trend_candidates` → черновой Markdown-отчёт
  в `report_runs` со статусом `completed`.
- Отчёт читается человеком за 15–20 минут.
- Dev-прогон: fetch_url на локальной Ollama; кластеризация — на DeepSeek (qwen3
  «думающий» слишком медленный/нестабильный на JSON — см. итог ниже).

## Шаги (по порядку)

1. [x] **Эмбеддер bge-m3.** Замена `StubEmbedder` на реальный локальный bge-m3
   (1024-dim). Загрузка модели ленивая; эмбеддинги кэшируются (файл/`sqlite`), чтобы
   не пересчитывать на каждом прогоне.

2. [x] **LLM-клиент.** Замена `StubLLM` на OpenAI-совместимый клиент с настраиваемым
   `base_url`. `.env` получает `LLM_BASE_URL` + `LLM_MODEL` (dev → Ollama
   `http://localhost:11434/v1`, прод → DeepSeek напрямую). Пакет `openai` уже в
   зависимостях.

3. [x] **fetch_url-коллектор.** Источники с `method: fetch_url` (dlnews, bankless,
   incrypted, rbc_crypto, habr_crypto, research, regulators, governance_social):
   `httpx` забирает страницу, LLM извлекает заголовок/резюме/дату. Fail-open на
   каждом источнике.

4. [x] **Поисковый провайдер (RU).** `YandexSearchProvider` за портом `SearchProvider`;
   активируется только при наличии `YANDEX_SEARCH_API_KEY`/`YANDEX_FOLDER_ID`, иначе
   фаза пропускается.

5. [x] **Отбор по зоне.** Эмбеддинги сигналов сравниваются с «профилем зоны»
   (эмбеддинги `seed_keywords` + `name`) косинусной близостью; ниже порога — отсев.
   Дедупликация URL по нормализации.

6. [x] **Кластеризация.** LLM группирует отобранные сигналы зоны в кандидаты
   (`TrendCandidate`): имя, определение, зрелость, номера каталога. Запись в
   `trend_candidates`. Реализовано **чанками по 40 сигналов + ретрай** — на больших
   списках LLM стабильнее отдаёт JSON (см. замечания ревью ниже).

7. [x] **Сборка дайджеста.** Markdown-отчёт по структуре §9 требований (без верификации):
   резюме, тренды с тезисами и источниками, слабые сигналы, список источников.
   Запись в `report_runs.report_md`.

8. [x] **Конвейер M1.** `collect → filter → cluster → draft report` (реальные),
   `research/verify` остаются pass-through. Прогон по всем 10 зонам — CLI `run --all`.

9. [x] **Тесты.** `test_embedder` (детерминизм/размерность), `test_llm_client`
   (mock-ответ), `test_filter` (порог/дедуп), `test_pipeline_m1` (stub-источник +
   stub-LLM), `test_config` (LLM_BASE_URL из env).

10. [x] **Веб-UI.** Просмотр отчёта прогона (`GET /report/{id}` уже есть) + вывод
    кандидатов зоны. Прогон по-прежнему запускается из CLI/UI.

## Замечания ревью M1 (зафиксировано)

1. **Память (D-14).** См. [decisions.md](../docs/decisions.md): bge-m3 — в сабпроцессе с
   выходом, Ollama — `OLLAMA_KEEP_ALIVE=1m`; две модели не резидентны одновременно;
   при давлении — `qwen3:8b`.
2. **Кэш эмбеддингов.** Шаг 1 упоминает кэширование, но `BgeM3Embedder` не кэширует —
   каждый прогон пересчитывает заново. Для M1 терпимо (сигналы каждый раз новые);
   вернуться при росте объёма.
3. **`tools` не прокинут.** `OpenAILlmClient.complete` принимает `tools`, но не передаёт
   в API. Для M1 (кластеризация без тулзов) ок; на M2 прокинуть для agentic loop.
4. **`LLM_MODEL_PRO`.** В `.env.example` есть, в `config.py` нет поля `llm_model_pro` —
   добавить, когда понадобится PRO-модель для сложных фаз (M2+).
